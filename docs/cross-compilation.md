# Cross-compiling for R-Car

The legacy C EdgeAgent is built by Yocto: its recipe inherits the SDK compiler,
sysroot, and machine tuning, then produces one runtime-selected binary. The Rust
agent follows the same model. Gen3, Gen4, and Gen5 do not use separate Cargo
features; `device.generation` in `config.toml` selects behavior at runtime.

## Supported build paths

Use one of these paths:

1. **Installed Yocto SDK**: use `scripts/cross-build.sh` for a standalone ELF
   and deployment bundle.
2. **Full Yocto image build**: add the recipe under `packaging/yocto` to the
   platform layer and run BitBake. This is preferred for production images.

Do not use a host-native `cargo build --release` binary on an R-Car target.

## Host prerequisites

- Linux build host with Bash 4 or newer.
- Rust and Cargo supporting edition 2024.
- The required Rust standard-library target installed through `rustup`.
- A matching R-Car Yocto SDK generated by the board BSP.
- `file`, `sed`, and `sha256sum`.

Generate and install an SDK from the corresponding BSP when one is unavailable:

```sh
bitbake <image-name> -c populate_sdk
./tmp/deploy/sdk/<sdk-installer>.sh
```

The installed SDK provides an `environment-setup-*` file. The cross-build
script sources that file in an isolated subshell and consumes `CC`, `AR`,
`LDFLAGS`, and `SDKTARGETSYSROOT`.

Paths such as `/opt/rcar-gen5/environment-setup-aarch64-poky-linux` below are
examples. They exist only after installing the corresponding vendor SDK. List
real SDKs visible to the script with:

```sh
scripts/cross-build.sh --list-sdks
```

`rustup target add` installs Rust's target standard library only. It does not
install a C cross-linker, libc, or sysroot.

## Target triples

Most 64-bit R-Car Gen3, Gen4, and Gen5 Linux BSPs use:

```text
aarch64-unknown-linux-gnu
```

The script does not assume that every BSP has the same ABI. It infers these
Rust targets from the SDK compiler name:

| SDK compiler family | Rust target |
| --- | --- |
| `aarch64-*-linux-*gcc` | `aarch64-unknown-linux-gnu` |
| `aarch64-*-musl-*gcc` | `aarch64-unknown-linux-musl` |
| `arm-*-gnueabihf-gcc` | `armv7-unknown-linux-gnueabihf` |
| `arm-*-gnueabi-gcc` | `armv7-unknown-linux-gnueabi` |

Override inference with `--genN-target` when the BSP uses a nonstandard
compiler name. The selected Rust target must match the target image's CPU ABI,
libc, and dynamic loader.

## Build one generation

```sh
rustup target add aarch64-unknown-linux-gnu

scripts/cross-build.sh \
  --generation 4 \
  --sdk-env /actual/sdk/path/environment-setup-aarch64-poky-linux
```

The shorter form can install the Rust target when needed:

```sh
scripts/cross-build.sh -g 5 --sdk-env /actual/gen5-sdk/environment-setup-aarch64-poky-linux --install-target
```

For a quick generic AArch64 GNU/Linux build on Debian/Kali, install the distro
cross-toolchain:

```sh
sudo apt-get update
sudo apt-get install gcc-aarch64-linux-gnu libc6-dev-arm64-cross
rustup target add aarch64-unknown-linux-gnu
scripts/cross-build.sh --generation all --target aarch64-unknown-linux-gnu --allow-generic
```

This generic toolchain is useful for development, but its glibc can be newer
than an existing target image. Never deploy these generic bundles without
checking their manifest against the target. Use that image's Yocto SDK for
release artifacts.

A static musl build avoids the target's glibc entirely when a matching Yocto
SDK is unavailable. Install an AArch64 musl cross-compiler and run:

```sh
rustup target add aarch64-unknown-linux-musl
scripts/cross-build.sh \
  --generation 4 \
  --target aarch64-unknown-linux-musl
```

The builder rejects a musl bundle if the resulting ELF is not static. Validate
it on the actual Gray Hawk image before treating this fallback as production.

## Build all generations

Use separate SDKs when the BSP releases or machine tuning differ:

```sh
scripts/cross-build.sh --generation all \
  --gen3-sdk-env /actual/gen3-sdk/environment-setup-aarch64-poky-linux \
  --gen4-sdk-env /actual/gen4-sdk/environment-setup-aarch64-poky-linux \
  --gen5-sdk-env /actual/gen5-sdk/environment-setup-aarch64-poky-linux
```

Environment variables are equivalent and are convenient in CI:

```sh
export RCAR_GEN3_SDK_ENV=/actual/gen3-sdk/environment-setup-aarch64-poky-linux
export RCAR_GEN4_SDK_ENV=/actual/gen4-sdk/environment-setup-aarch64-poky-linux
export RCAR_GEN5_SDK_ENV=/actual/gen5-sdk/environment-setup-aarch64-poky-linux
scripts/cross-build.sh --offline
```

Use `--sdk-env` only when one installed SDK is intentionally valid for every
selected generation. Use `--dry-run` to validate selection and target inference
without invoking Cargo.

## Output

Each generation is isolated below `dist/`:

```text
dist/gen4/
├── edgeagent-rs
├── config.toml
├── edgeagent-rs.service
├── build-manifest.txt
└── SHA256SUMS
```

The generated config sets the requested generation and removes the default
`device_type`, allowing runtime board-model detection. It also removes the
placeholder API token. Before deployment, set the FarmController URL, network
interface, and protected `EDGEAGENT_API_TOKEN` environment value.

`build-manifest.txt` records the SDK, sysroot, compiler, Rust target, ELF
architecture, linkage, and required GLIBC symbol versions. `SHA256SUMS` covers
the complete bundle.

## Full Yocto build

The template recipe is `packaging/yocto/edgeagent-rs_0.1.0.bb`. A production
recipe must provide an offline dependency source using the BSP layer's standard
Cargo vendoring workflow. Place the source archive, systemd unit, and
board-specific `config.toml` in the recipe's `files/` directory, then add the
package to the image:

```bitbake
IMAGE_INSTALL:append = " edgeagent-rs"
```

Build in each BSP environment:

```sh
bitbake edgeagent-rs
```

Remove the legacy `dev-agent` and `startup-script` packages from the image to
avoid two services binding TCP 8888.

## Troubleshooting

- **Rust target not installed**: run `rustup target add <triple>` or pass
  `--install-target`. This does not install the linker.
- **Cross-linker not found**: source the correct SDK with `--sdk-env`; do not
  substitute a compiler for another BSP release. For development on Debian or
  Kali, install the package printed by the script.
- **SDK environment does not exist**: the documented `/opt/rcar-*` names were
  examples. Run `scripts/cross-build.sh --list-sdks`, or generate and install
  an SDK from the matching BSP with `bitbake <image-name> -c populate_sdk`.
- **`GLIBC_x.y not found` on target**: the SDK is newer than the target image.
  Run `getconf GNU_LIBC_VERSION` on the target and compare it with
  `glibc_requirements` in the bundle manifest. Rebuild with the SDK generated
  from that exact image/BSP; do not replace libc files on the target.
- **Wrong ELF architecture**: inspect `build-manifest.txt`; verify the SDK and
  any `--target` override.
- **Crates unavailable with `--offline`**: vendor/fetch dependencies before the
  isolated build or use the Yocto recipe's vendored Cargo source.
- **TLS requests fail on target**: install CA certificates and verify target
  time. Rustls does not remove the need for a valid root store and clock.
